为什么需要 · 01

AI 与 HPC 的存储，和普通文件服务不在一个量级

数据集以 PB 计、带宽以 TB/s 计、成百上千个节点同时读写。规模到了这一步，常见的四类问题会同时出现。

数十 PB活跃数据集规模，并且持续增长
TB/s上千张 GPU 时的聚合带宽需求
1,000s并发读写的客户端数量，元数据与一致性成为关键
01 · GPU UTILIZATION
加速卡空等
存储喂不饱 GPU。在 AI 工厂里，GPU 空闲时间是最贵的一项开销。
02 · METADATA
小文件拖住流水线
数据加载、checkpoint 重启、目录列举会卡住，即使带宽远未打满。
03 · CAPACITY ECONOMICS
PB 级全闪太贵
纯全闪设计成本高；把数据在独立分层之间来回搬，又会拖慢研究人员和流水线。
04 · OPERATIONS
横向扩展存储难运维
内部专家稀缺，升级风险高，部署、升级、支持各环节容易被锁定。

对应到制造业的典型负载

CAE 仿真：结构、流体、碰撞仿真的大规模并行求解与结果写出
自动驾驶仿真与训练：海量路采视频、点云与仿真场景的高并发读取
工业视觉模型训练：多 GPU 训练读取样本、周期性写 checkpoint

源材料列举的负载为 HPC 仿真建模、AI 训练与 AI 推理（KV cache 复用）；上述制造业场景是具备同类访问模式的工作流，需结合实际负载验证。

Lustre 原理 · 01

三类服务，各配一类存储目标：元数据与数据分路

Lustre 是开源、POSIX 兼容、基于对象的分布式并行文件系统。点击下方按钮，看一次文件访问依次经过哪些服务。

三类服务的分工

MGS + MGT：客户端最先联系它来定位文件系统各项服务；每个命名空间一对 HA。
MDS + MDT：拥有命名空间，记录目录、文件名与文件位置。增加 MDS/MDT 对来提升元数据性能。
OSS + OST：承载文件数据。这里的"对象"是 Lustre 对象（一个文件或文件的一段），不是 S3 对象。增加 OSS/OST 组来提升带宽与容量。

部署上的灵活度

MDS 与 OSS 可以合设在同一组服务器上
MDT 与 OST 可以放在同一套阵列上
Lustre 自身不做数据冗余，依赖 MDT / OST 所在存储的可靠性，这正是 E-Series 的定位
Lustre 原理 · 02

条带化：一个文件拆到多个目标上，单个作业同时取所有带宽

拖动滑块改变条带数，看文件分段如何分布到各个 OST，以及单个作业能拿到的相对带宽。

一个命名空间，三项机制

跨目标条带化：一个文件切分到多个 OST，单个作业同时从所有目标拉带宽。
元数据独立于数据路径：目录与小文件操作走自己的路径，可以独立扩展。
混合介质同一挂载点：SSD 与 HDD 可以组织成同一命名空间内的不同池，性能和容量在一个挂载点下统一管理。

混合池带来的取舍

闪存池：热数据集、训练样本、checkpoint 写入
HDD 池：大文件顺序读写，HDD 条带化后也能提供高带宽，不必把数据跨层搬来搬去
E4000 可接最多 300 块 NL-SAS 盘，承担容量池；EF80 承担性能池

NetApp Lustre · 04

一次加一个构建块：容量与带宽线性增长

每个构建块是一个独立故障域，所有构建块共用一张客户端网络。第一个构建块承载 MGS 与 MDT，后续构建块把各自的 MDT / OST 注册到同一个 MGS 下。

最大 HDD 容量
机架空间 · 网络上联

扩展数值由一个已验证的 2×2 构建块按比例推算，实际结果取决于配置与负载。

扩展规则

基础构建块：每个文件系统都需要一个，承载 MGS、MDT 和 OST 容量
扩展构建块：把自己的 MDT / OST 注册到基础构建块的 MGS
2–5 个构建块（4–10 个文件节点）组成一个 HA 集群，多个 HA 集群可以合成一个文件系统
独立型与融合型构建块可以混用，分别调元数据容量、元数据性能（stat / open / close）与带宽 / IOPS

对规划的意义

首期按当前 GPU 规模配置，后续按块追加，无需推倒重来
容量需求大于带宽需求时，用 HDD 扩展容量池即可

PB 级并行文件系统怎么备份

单台备份服务器面对 PB 级文件系统会立刻成为瓶颈
路径 A：POSIX HSM 策略引擎（Lustre 分层引擎），由各计算节点上的数据搬运器并行写出
路径 B：并行备份软件（如 Commvault、Atempo Miria）
目标层为 StorageGRID，经 HTTPS S3 写入，启用 S3 Object Lock 获得对象层的网络韧性
