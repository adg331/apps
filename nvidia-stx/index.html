背景 · 01

先讲清楚一件事：KV Cache 为什么会撑爆显存

这是整个话题的起点。不理解这一层，后面所有架构差异都无从判断。

上下文长度 128K
并发会话 40 路

上图数值为示意估算，非性能承诺；实际取决于模型结构、精度与并发模式。一个可复算的实测锚点：NetApp 公开的 Qwen3-4B-Instruct-2507（36 层 / 8 KV 头 / 头维度 128 / bf16）为 144 KB / token，一个 10 万 token 的会话 KV 约 14 GB已验证。模型越大，这个数字越高。

用一个类比说清楚

模型读一遍上下文，会算出一份中间结果，这份中间结果就是 KV Cache。
它像会议纪要：只要留着，下一轮对话就不用把前面所有内容重新读一遍。
问题是它很大：长文档、多轮对话、AI 智能体连续工作，纪要会一直变长。
显存放不下时，系统只能把纪要丢掉。下次用户再问，模型必须从头重读一遍——算力白烧，用户等更久。

对企业业务意味着什么

客服知识库问答：同一份产品手册被反复重读，每次都付一遍算力
合同 / 工单长文档处理：几十页文档每轮追问都要重扫
研发助手多轮会话：对话越长越慢，用户体验递减
AI 智能体连续作业：跨步骤、跨会话的记忆无处存放
现象一
首字变慢
用户按下回车到看到第一个字的时间（TTFT）随上下文线性增长
现象二
并发上不去
显存被 KV 占满，同一批 GPU 能服务的会话数下降
现象三
算力重复消耗
重算已经算过的上下文，是纯粹的重复付费
共同根因
显存墙
HBM 最快，但容量最小、最贵、扩不动
背景 · 02

NVIDIA 把存储位置编了号：G1 到 G4

这套编号是后面所有讨论的共同坐标系。它和传统存储分层不是一回事——它衡量的是"离 GPU 有多近"。已公开验证

点击查看每一层的定位
当前选中层其他层

G1 · GPU HBM 显存

正在生成 token 时用到的、延迟最敏感的那部分 KV。速度最优，但容量是整个体系里最紧张的资源。

存什么：活跃生成中的 KV
局限：容量小、成本高、无法横向扩展

NVIDIA 对这套分层的官方判断

G1–G3 加起来还是不够：推理规模上去后，KV 容量随 GPU 数量增长，但仍覆盖不了全部需求
压到 G4 代价太大：毫秒级延迟 + 功耗上升，把活跃 KV 放这里会直接拖慢推理
G3 还有个结构性问题：本地 SSD 绑死在单台机器上，负载一漂移，缓存就白存了

分层命名与判断均引自 NVIDIA CMX 官方技术博客。

背景 · 03

NVIDIA 的答案：在 G3 和 G4 之间插一层 G3.5

这一层就是 CMX。它是本次所有架构讨论的物理载体。已公开验证

当前：加入 G3.5
新增层 G3.5 / CMX KV 溢出路径

G3.5 想同时满足两个矛盾要求

足够大：能装下一个可扩展单元（SU）里许多智能体同时演进的上下文，PB 级
足够近：能在解码阶段之前把上下文预先搬回 GPU / 主机内存，不造成停顿
足够省：以闪存为介质，比把同样数据压在通用共享存储上更省电
连带好处：G4 可以回归本职——只放真正需要长期留存的历史与审计数据

NVIDIA 公布的指标 厂商声明

5×每秒出字数（TPS）
5×能效（每瓦出字数）
2×数据摄取速度

均为 NVIDIA 对比"传统 CPU 架构存储"给出的方向性目标，截至目前没有独立第三方基准验证，不应作为性能承诺引用。

先把量纲落地
144 KB / token已验证
NetApp 公开的算式：KV 头数 × 头维度 × 2（K＋V） × 精度字节 × 层数。以 Qwen3-4B-Instruct-2507 计得，可自行复算
单个会话
10 万 token ≈ 14 GB已验证
一路长上下文会话的 KV 就是这个量级。模型越大越高——这是 4B 级模型的值
所以需要 G3.5
HBM 装不下，G4 又太慢
按上面的量级往 SU 级并发外推，总量很快进入 TB–PB 区间本篇算术，非厂商结论。中间必须有一层既装得下、又够近的介质

两条路线 · 02

第 1–2 层：这两层两侧是对得上的

LMCache、KVBM、Everpure KVA 属于同一功能层，互相可替换。这是全篇唯一一处两侧完全对等的地方。已公开验证

当前：LMCache

第 1 层 · 推理运行时与编排

左：vLLM——主流开源推理引擎，NetApp 全部公开测试都基于它
右：Dynamo——NVIDIA 分布式推理服务框架，会把请求路由到"已经存有对应上下文"的节点
右：Grove——再往下一层的调度器，按上下文所在位置放置负载，负载迁移后仍能复用缓存
可组合：vLLM 可以跑在 Dynamo 之下，两者不互斥

第 2 层 · KV Cache 管理（同层可换）

共同职责：KV 块的索引、生命周期、复用判定、逐出、卸载与分层
LMCache：厂商中立，自带 CPU 内存 / 本地盘 / Redis / S3 / GDS / NIXL 等多种后端
KVBM：内部分三层——运行时连接器 → 块管理 → NIXL 传输
Everpure KVA：与 LMCache 同层的第三种实现，但是厂商自研、不开源，后端只指向自家 FlashBlade已验证
常见误解：DOCA Memos 不属于这一层，它在更下面的第 4 层
两条路线 · 03

第 3–4 层：左侧无直接对应的两层

这是两条路线分岔的真正位置。NVIDIA 在 KV 管理层与存储协议之间，多插了两层专门的抽象。

第 3 层 · NIXL — 数据移动抽象 已公开验证

它不是存储协议，是一个"搬运抽象层"：屏蔽 GPU 显存、主机内存、文件、对象、块设备之间注册与传输方式的差异。
插件架构。官方仓库现有插件：ucx · libfabric · gpunetio · uccl · posix · cuda_gds · gds_mt · obj · azure_blob · hf3fs · mooncake · gusli · infinia
存储厂商的接入点就在这里：写一个 NIXL 插件，就进入了 NVIDIA 的推理数据通路。
名称注意：NVIDIA 官方两种写法并存——代码仓库标题为 Inference Xfer Library，技术博客写作 Inference Transfer Library。同一个东西。

第 4 层 · DOCA Memos — Context/KV 存储服务 已公开验证

官方定义：面向 BlueField-4 与 CMX 优化的 SDK，跨"AI 计算节点"与"CMX 数据节点"管理并共享 KV Cache。
对外接口是键值 API，把以太网直连的闪存变成 SU 级共享缓存层；应用侧保持无状态，路由与复用由 CMX 负责。
硬件加速：数据完整性校验与加密在 BlueField 芯片内完成，不占主机 CPU。
为什么左侧没有对应物：ONTAP 提供的是文件与对象语义，不提供 KV 语义服务。KV 块在写出前必须先被序列化成普通文件或对象。

NIXL 与 DOCA Memos 到底谁调用谁？—— 这是全篇最容易讲错的一点

已公开验证
代码层面：NIXL 在上，DOCA Memos 在下。NVIDIA 官方 NIXL 仓库存在一个名为 DOCA_MEMOS 的后端插件，链接 libdoca_kv，操作对象是 NVMe KV 设备，支持 STORE / RETRIEVE / EXIST 三种操作。
状态提示
该插件的代码提交仍处于未合入状态（提交于 2026-06，最后更新 2026-08，尚未并入主干）。因此不能说"NIXL 已发行版支持 DOCA Memos"。
需要保留的不确定性
NVIDIA 至今没有发布一张官方分层图。官方文字是协同口径："DOCA Memos 对接推理框架 … 并借助 NIXL 与 Dynamo 实现跨节点共享"，同时"支持开放接口"。VAST 的公开实现就绕开了 Memos 的 KV 接口，改用文件接口。
两条路线 · 04

第 5–8 层：BlueField-4 出现在数据路径的两端

这是右侧路线在硬件形态上与传统存储最本质的不同。已公开验证

当前：STX / CMX

第 5 层 · 协议：CMX 数据面到底跑什么

NVMe / NVMe-oF，并且明确包含 NVMe KV 扩展——可以直接按 key 存取，不必先转成文件或块
object / RDMA——NVIDIA 原文用词。推测第三方推断这是 S3-over-RDMA，NVIDIA 未确认
官方原话：BlueField-4 运行 KV I/O 平面，"高效终结 NVMe-oF 与 object/RDMA 协议"

一个容易混淆的细节

NetApp AFX 内部也用 NVMe-oF over RoCE——但那是控制器与存储柜之间的内部总线，不向 GPU 暴露。
客户端看到的仍然是 NFS / SMB / S3。因此这条 NVMe-oF 与 CMX 数据面的 NVMe-oF 不是一回事，不能混为一谈。
第 5 层
协议
NVMe / NVMe-oF（含 NVMe KV 扩展）＋ object/RDMA，由 BlueField-4 终结
第 6 层
网络
Spectrum-X 以太网提供无损 RoCE、拥塞控制与自适应路由
第 7 层
处理器
BlueField-4 STX = Vera CPU + ConnectX-9 SuperNIC，双端部署
第 8 层
介质
CMX 机柜内 NVMe SSD，即新增的 G3.5 层，SU 内共享
两条路线 · 05

如果只记住一句话：差别不在 RDMA，在数据语义

两条路线都用 RDMA、都用以太网、都用 NVMe SSD。分水岭是 KV 块离开 GPU 之后，还保不保持它原本的键值形态。

当前：文件语义

左路线的取舍

今天可落地：NetApp 已发布可复现的配置与基准，标准协议，无专有客户端已验证
无绑定：不依赖特定 GPU 代次、特定交换机、特定 DPU已验证
上限受限于文件语义：存储侧看到的是文件，做不了 KV 级的复用与路由已验证

右路线的取舍

性能上限更高：KV 语义一路保持到 NVMe KV 设备，主机 CPU 完全不在数据路径上推测
耦合更深：绑定 Rubin GPU 机架、Spectrum-X 以太网、BlueField-4已宣布
时间点：合作伙伴平台 2026 下半年交付，目前全行业无 GA 产品已宣布
证据与状态 · 01

四个最容易讲错的问题，按官方原文校准

这四条是与客户或同行讨论时最常出现分歧的地方。每条都注明证据强度。

问题结论状态
KVBM 与 DOCA Memos 是不是直接上下级？ 不是。NVIDIA 从未画出 KVBM 直接调用 DOCA Memos 的关系。官方只说"Dynamo 用它的 KV 块管理器连同 NIXL来编排上下文在各层之间移动，把 CMX 当作 KV Cache 的上下文内存层"。中间隔着 NIXL。 已验证
NIXL 与 DOCA Memos 谁调用谁？ 代码层面是 NIXL 调用 DOCA Memos。NIXL 仓库中存在 DOCA_MEMOS 后端插件（链接 libdoca_kv，操作 NVMe KV 设备）。但该提交尚未合入主干；同时官方文字仍是协同口径，并声明 Memos "支持开放接口"。 已验证
未合入
CMX 数据面用哪些协议？ NVMe / NVMe-oF（含 NVMe KV 扩展）＋ object/RDMA，两者都承载在 Spectrum-X 的无损 RoCE 之上。"object/RDMA 就是 S3-over-RDMA"属于第三方推断，NVIDIA 未确认。 已验证
部分推测
BlueField-4 在两侧各干什么？ 计算侧：Rubin 节点内的 DPU 运行 KV I/O 平面与控制面，终结存储协议，减少主机 CPU 参与与内存拷贝。存储侧：CMX 机柜内的控制器直接管理 NVMe SSD、运行存储服务、卸载完整性校验与加密。 已验证

必须保留的两处不确定性 推测

NIXL 与 DOCA Memos 的确切分工——NVIDIA 至今未发布官方分层图。业内公开分析用的措辞是"probably / likely"，未合入的代码插件是目前唯一硬证据。
第三方厂商是否必须走 DOCA Memos——VAST 公开的 CMX 实现用文件接口（virtio-fs）作为控制面入口，与 NVIDIA "DOCA 暴露 KV API"的表述不一致，说明存在多条合法接入路径。

沟通建议

可以讲："NVIDIA 定义了 G3.5 上下文层，数据面用 NVMe-oF 与 object/RDMA，BlueField-4 在计算与存储两端都参与。"
不要讲："KVBM 直接调用 DOCA Memos"、"NIXL 已正式支持 DOCA Memos"、"CMX 用的是 S3-over-RDMA"。这三句都超出了公开证据。
证据与状态 · 02

NetApp 今天真正可复现的四条路径

前三条基于 LMCache；第四条是 vLLM 原生卸载连接器（上游 2026-01 发布，NetApp 2026-08 实测）——连 LMCache 都不需要，共享存储在它眼里就是一个挂载点。四条全部使用标准协议，配置文件与基准命令均已公开，客户可自行复现。已公开验证

pNFS over RDMA 的公开观测值

+201%聚合处理速度（最高）
−99%平均首字延迟（最高）
+223%单请求解码吞吐（最高）

大字对比不做卸载，虚线下对比 GPU＋CPU 卸载；均为原文"最高"观测值，非承诺。

NetApp 官方立场原文

"NetApp 用行业标准协议与工具支持 KV Cache 卸载。不需要任何专有客户端。你可以继续使用多年来一直在用的 NFS 与 S3 协议 … 在网络条件允许时，我们当前的建议是使用 pNFS over RDMA。网络不允许 RDMA 时，ONTAP S3 与 pNFS over TCP 都是很好的选择。"

直通更快，为什么推荐的却不是 GDS

LMCache 进程内模式下，GDS 后端不建议与 CPU 内存层并用——用了直通，就得放弃 G2，只剩两层。pNFS 路径没有这个限制，三层可以同时开。已公开验证

"进程内"＝LMCache 作为库跑在 vLLM 推理进程里；"MP 模式"＝单独起一个缓存服务进程，vLLM 去连它。G1 由 vLLM 自己管理，LMCache 负责 G2 和外部存储。

为什么不能并用 本篇推测

LMCache 文档只写了"有时建议关闭 CPU 内存卸载"，没有给原因已验证
我们的理解：GDS 的价值是绕过主机内存。进程内开着 CPU 层时，KV 会先从显存拷进主机内存（为了留在 G2），再从那里写往存储——直通被绕回了主机内存，还多一次拷贝，并争用锁页内存与 PCIe 带宽推测

换成存储语言

这就是 O_DIRECT 与页缓存不能兼得：要直通，就别指望中间那层缓存；要缓存，数据就得经主机内存中转。
所以"用 GDS 就更快"不成立——要看它让你丢掉了什么。
丢掉的代价
中等长度靠 CPU 层已验证
NetApp 单实例实测：提示在 6k–21k token 时只开 CPU 内存层更好，26k 以上外部存储才占优。GDS 方案丢掉的正是收益最大的那一段
MP 为什么能三层
分层由独立进程统一管
缓存服务进程负责全部层级，GPU、CPU、GDS 可同时启用。它卡住的是另一件事：2026-08 测试时不支持被抢占请求的恢复，长提示下更慢
上游进展
抢占已修复，未重测已验证
抢占处理已随 LMCache v0.5.6 正式版（2026-10-14）发布；NetApp 尚未发布重测结果，推荐结论不变
结论
要三层又要稳，走 pNFS
GDS 不是不好，而是在当前 LMCache 实现里，进程内用它就得牺牲 CPU 层。这是 NetApp 推荐文件接口路径的原因
证据与状态 · 04

把 KV Cache 翻译成存储语言：对象多大、要几次 I/O

NetApp 2026-06 公开的长上下文调优结果。结论反直觉：LMCache 的默认参数在远端存储 ＋ 长上下文下会把 vLLM 集群跑到不稳定——这是厂商自己写下的负面结论，算式全部公开、可自行复算。已公开验证

一个 token 占多少字节 —— 可自行复算

每 token 每层 ＝ KV 头数 × 头维度 × 2（K＋V） × 精度字节
8 × 128 × 2 × 2 = 4,096 B
每 token ＝ 上式 × 层数
4,096 × 36 = 147,456 B ≈ 144 KB / token
换算成存储对象：chunk 256 → 36 MB；张量并行 4 卡时每卡各写一份 → 4 个 9 MB 对象

NetApp 的结论与它的边界

测了 256 → 4096，2048 是甜点位：I/O 次数降到 1/8，传输总量一个字节没变
超过 2048 收益递减：chunk 太大后，命中粒度本身开始反噬
边界要讲清楚：这是 Qwen3-4B ＋ 4 卡 ＋ 10 万 token 的结论。换模型、换并行度必须重算——好在算式已公开，客户可以自己算。
现场最能用
默认值不能直接上已验证
厂商自己公开写明默认参数会把集群跑崩，并给出推荐值。这种自曝比任何性能数字都建立信任
换成你熟的话
这是一道 I/O 题
同样 14 GB 数据：1,560 次 9 MB 的小操作，还是 192 次 72 MB 的大操作——后者才是共享存储擅长的形态
为什么会崩
每次操作的固定开销
远端后端每个 chunk 都是一次独立网络往返，chunk 太小时单次开销压过了带宽本身
必须补的限定
数字随模型变
144 KB / token 是 4B 级模型的值，模型越大越高。引用时一定要连模型一起讲

"NetApp 是 STX 合作伙伴"与"NetApp 产品已经是 STX 架构"，是两件完全不同的事。

已经确认存在的

NVIDIA 官网 STX 合作伙伴墙有 NetApp，GTC 2026 新闻稿也列入存储厂商名单

两条路线的适用前提

标准协议路线 · 今天可落地
本栏依据：已公开验证

什么情况下选它

推理集群不是 Rubin 机架：现有 GPU 存量设备，或混合代次
网络不是 Spectrum-X：通用以太网 / 已有 RoCE 环境

需要接受的：存储侧不理解 KV 语义，性能上限低于原生路线推测

客户这样问可以讲的（有公开来源）到此为止 / 不能讲
"你们支持 NVIDIA STX 吗？" NetApp 在 nvidia.com 的 STX 与 CMX 两个合作伙伴墙上都在列已验证；官方表态原文是 "will support NVIDIA STX"已验证；INSIGHT 2026 场次 BKO1025 上与 NVIDIA 同台，说明正与 NVIDIA 软硬件团队及 ODM 联合研发上下文内存存储已宣布 无架构图、产品名、时间表，问型号和时间如实说无公开信息。联合研发是方向声明，不是产品。
"DDN 的插件都进 NVIDIA 官方发行版了，你们呢？" 属实。DDN 的 Infinia 插件自 NIXL 1.3 起随标准发行版打包，并含在 Dynamo 容器内已验证。NetApp 目前没有 NIXL 上游插件已验证——查 ai-dynamo/nixl 主干 src/plugins 目录零命中。但"没插件"不等于"接不上 NIXL"：NetApp 已验证过经 NIXL 自带的通用 GDS 插件写 ONTAP pNFS 的两条路径（LMCache MP 模式的 nixl_store_dynamic 后端、SGLang HiCache 的 GDS_MT），路径是通的已验证 不要暗示"我们也在做"专有插件。两条都不是推荐方案，LMCache MP 那条 NetApp 明确不推荐；"上游已修好抢占"属实（v0.5.6），但 NetApp 未重测。
"Everpure 的 KVA 已经在卖了。" 属实，但要把层次讲清楚：KVA 与 LMCache 是同一功能层，底下是未经改造的标准 FlashBlade，走 NFS / GDS已验证。也就是说 Everpure 和 NetApp 走的是同一条标准协议路线，差别是自研闭源 vs 开源中立。NetApp 侧的 LMCache + pNFS over RDMA 配置与基准已公开、可复现已验证 KVA 有厂商数字（20× / 6×；9-30 那次无测试配置），NetApp 侧没有同口径数据，不要口头比性能。
"VAST 已经把 CMX 落地架构讲清楚了。" 属实，VAST 是唯一公开 CMX 实现细节的厂商（CNode 移植进 GPU 服务器的 BlueField-4）已验证。但它同样没有 GA 产品已验证 "公开了架构"不等于"能买到"。别把这条讲成 VAST 已经落后于交付。
"你们 +201% 是跟什么比的？" 跟不做卸载比。同篇博文另有对比已开 CPU 卸载的一组：最高 +157% / −86% / +174%已验证 客户多半已开 CPU 卸载，引第二组更稳。
"CMX 说能快 5 倍、省 5 倍电。" 这是 NVIDIA 声明的方向性目标，不是可复现的观测值已宣布。目前无任何第三方基准已验证 不要拿它跟 NetApp 的任何数字对比——基准口径与量纲都不同，对比本身就不成立。
"你们这套是不是绑死在 LMCache 这个开源项目上？" 不是。vLLM 自 2026-01 内建了原生卸载连接器（OffloadingConnector），支持 CPU 内存 + 任意本地挂载文件系统已验证。NetApp 已按这条路径公开测过 ONTAP pNFS over RDMA，并把它列为两条推荐路径之一已验证——此时存储侧连"KV Cache 软件"都不存在，就是一个挂载点 不要引申成"所以 NetApp 比别家先进"。这个连接器是 vLLM 上游（IBM Research 团队）做的，任何文件存储都能用，不是 NetApp 的差异化能力。
"这套东西能不能直接上生产？" 能，但默认参数不能直接上。NetApp 已公开写明：LMCache 默认 chunk_size=256 在长上下文 ＋ 远端后端下会造成超时、部分请求无响应、vLLM 集群不稳定；实测应调到 2048，I/O 次数降到 1/8已验证。换模型换并行度要重算，算式 NetApp 也公开了 不要把"要调参"讲成小事就带过。它是部署前置条件，客户按默认值上线是会出故障的。也不要把 2048 讲成通用值——那是 Qwen3-4B ＋ 4 卡的结论。
"那 NetApp 什么时候能有？" 没有公开时间表，如实说不知道。能讲的公开状态只有"与 NVIDIA 联合研发中"（BKO1025）。然后把话接到今天能做的事上：vLLM 原生连接器或 LMCache + pNFS over RDMA / S3 / GDS，NetApp 已公开四条路径的配置与完整基准命令，客户可在自有环境复现已验证 一个时间暗示都不要给。"应该快了""研发快做完了"都是承诺。
永远可以讲
可复现的东西已验证
NetApp 公开了四条路径的启动参数与完整基准命令，还公开写明自家生态里哪一条目前不推荐。"你可以自己跑一遍"是唯一不需要任何前提的说法。
讲之前先加限定
已宣布的东西已宣布
合作伙伴身份、"will support STX"——讲的同时必须补一句"目前只有表态，无产品名与时间表"。
永远不要讲
时间与性能承诺
交付时间、跨厂商性能对比、"我们也在做"。这三类现场都没有公开证据可依，说了要自己担。
可以反过来用
标准协议不是退路已验证
Everpure 的 KVA、WEKA、VAST 今天在卖的方案都仍走标准文件 / 对象协议。这条路线是行业现状，不是 NetApp 独有的妥协。

本页只整理"有公开来源支撑的说法"。凡是本篇标为已宣布或推测的内容，现场都要连同不确定性一起讲；负面事实（如"NetApp 没有 NIXL 插件"）已注明检索渠道，被追问时可直接复述检索方式。

术语速查 · 02

六个核心概念的通俗解释

面向非 AI 背景的同事与客户。理解这六个，全篇内容就都能跟上。

概念 01
Token（词元）
模型处理文字的最小单位，约等于半个到一个汉字。"每秒出多少 token"就是 AI 的打字速度。计费也按它算。
概念 02
上下文（Context）
模型这一次能"看见"的全部内容：系统提示 + 历史对话 + 你贴进去的文档。上下文越长，模型知道得越多，但代价也越大。
概念 03
KV Cache
模型读完上下文后算出的中间结果。像会议纪要：留着，下轮就不用重读全部材料；丢了，下轮必须从头再读一遍。
概念 04
显存墙
HBM 显存速度最快但容量最小、最贵、扩不动。会议纪要越攒越多，显存先满——这就是整件事的起因。
概念 05
DPU / BlueField
插在服务器上的一块"小服务器"。像专职快递员：主 CPU 不用亲自跑网络和存储的活，专心算业务。
概念 06
KV 语义 vs 文件语义
文件语义：把纪要装进档案袋，按袋子编号存取。KV 语义：纪要直接按主题标签存取，存储系统认得它是什么。后者上限更高，但要求整条链路都支持。

用一个仓库类比串起全篇

GPU 显存（G1） = 工位桌面，伸手就够到，但只能放几份文件
主机内存（G2） = 工位旁的抽屉
本地 SSD（G3） = 本部门的文件柜，别的部门用不了
CMX（G3.5） = 新建的公共资料室，全楼共用，取件很快——这是 NVIDIA 新增的那一层
共享存储（G4） = 地下档案库，容量无限但取件慢

那么两条路线的差别是什么

NetApp 当前方案：公共资料室用的是标准档案袋——任何部门、任何流程都能直接用，今天就能建。资料室本身不知道袋子里装的是什么。
NVIDIA STX / CMX：公共资料室按主题标签直接管理每一份纪要，还配了专职管理员（BlueField-4）在两端收发。效率更高，但整栋楼的门禁、通道、管理员都得换成配套的那一套。
两者都用同一条高速通道（RDMA）。区别在于资料是以什么形态在通道里流动，以及谁在两端管理它。
