为什么是对象存储 · 01

对象存储已经从冷归档，变成应用的持久层

云原生应用把状态交给 S3：应用本身无状态、横向扩展，持久性、可用性和状态管理由对象存储负责。数据中心故障时，应用感知不到。

对象负载的变化

以前：备份、归档、媒体库，写一次很少读。
现在：数据湖、分析、AI 训练语料、Web 应用、IoT 与流数据，读写都频繁，对吞吐和小对象性能都有要求。
架构含义：对象存储需要像公有云一样多可用区双活、单一端点、对应用透明地容忍故障。

对制造业的意义

车间遥测与 IoT：设备日志、传感器数据以海量小对象持续写入，统一落到一个命名空间。
质量追溯：检测图像、批次记录长期保留，随时可被分析与审计调用。
为什么是对象存储 · 02

一个 grid 横跨多个站点，部署形态按需组合

一个 grid 最多 16 个站点、1 EB 容量，站点之间双活；多个 grid 还可以联邦成一个全局命名空间。节点可以是专用设备、VMware 虚拟机或裸金属，混合部署。

形态定位

型号与定位依据 BKO3011 场次资料整理，具体规格以产品文档为准。

16单个 grid 的站点上限
~10 EB多个 grid 联邦后的全局命名空间

像公有云一样运营

多租户：多级租户、配额、审计与计量，S3 IAM 桶策略与组策略。
流量隔离与 QoS：内置高可用负载均衡，按流量分级限速，防止个别应用拖垮全局。
不停机运维：升级、扩容、退役节点都在线完成。

冷数据的出口

可分层到 Amazon S3 / Glacier、Azure Blob、Google Cloud，或磁带库，取得最低存储成本。
数据管理 · 01

ILM 策略：放在哪里、存几份、保留多久

全局的信息生命周期管理（ILM）策略决定对象放到哪些站点、哪类介质，用复制还是纠删码保护，以及保留多久。策略变更后，后台扫描会自动把已有对象调整到位。选一种保护方式，看对象的分布和容量开销。

—存储开销（原始数据的倍数）
—可容忍的故障

示意：4+2 纠删码把对象切成 4 个数据片和 2 个校验片，分布在三个站点。实际片数与布局以所配置的纠删码方案为准。

策略可以细到桶

多套策略同时生效：如金、银、铜三档，用桶标签匹配。
租户自己选：租户能看到并选择自己数据的存放方式。
缩小误操作影响面：改一套策略，只影响打了这个标签的桶。

对制造业的意义

质量与追溯数据：三站点纠删码长期保存，用更低开销换更高持久性。
设备原始日志：近期数据留在本地，一年后自动分层到低成本介质。
数据管理 · 02

分支桶：像 Git 一样管理桶的版本

基于对象版本，按时间点从一个桶派生出新桶：回到某个时刻、排除某段时间写入的坏数据，或者把可疑时段单独隔离出来取证，原桶不受影响。选一种操作，看派生出的桶里有哪些版本。

典型用法

AI 数据集版本：main、develop、发布版本各一个分支，像代码一样管理训练数据。
勒索与误写恢复：把被破坏的时间窗口排除掉，得到一个干净的桶。
取证：把可疑时段单独派生出来交给安全团队，不影响生产。

版本状态

StorageGRID 12.1（2026 年 7 月）支持按时间点派生分支桶。
分支的合并与拆分在后续规划中。产品方向
数据管理 · 03

内外两圈：贴近 GPU 的缓存，加上海量容量层

外圈是 EB 级、单一命名空间的存储节点，对接多个 GPU 集群；内圈是靠近某个 GPU 集群部署的缓存节点，提供低延迟、高吞吐的加速层。元数据和数据也可以拆到不同节点各自扩展。

示意图依据 BKO3011 场次资料重绘。

元数据与数据分开扩展

混合节点：元数据和数据一起扩展，默认形态。
仅元数据节点：海量小对象时只扩对象数，或给慢硬件补上元数据处理能力。
仅数据节点：只扩容量。
~4×12.1 中 4 KB 小对象 PUT 的提升
60 亿12.1 中单节点对象数（提升 50%）

对制造业的意义

产线传感器、设备日志大多是 KB 级小对象。小对象写入性能和单节点对象数，直接决定能接入多少条产线。
安全与多站点 · 01

StorageGRID 12.1：多 grid 一个端点，关键变更多人审批

2026 年 7 月发布。重点是跨 grid 的联邦、更严格的变更管控与身份集成，以及对 AI 小对象负载的性能提升。按类别筛选。

全局命名空间：一个 S3 端点

多个 grid 共用一个全局端点（如 s3.company.com）。
每个租户的联邦连接数从 1 增加到 10；账户同步复制用户、组和访问密钥。
12.1 中 grid 之间不会自动故障切换，需要手动切换。

多管理员审批（MAV）

激活 ILM 策略这类高影响操作，必须另一位管理员批准后才执行。
请求 7 天过期，全流程留痕，满足审计要求。默认关闭，由 Root 启用。
安全与多站点 · 02

下一版本：对象级勒索检测，与自管密钥

对象写入时就在线检测可疑内容，自动告警并拦截；加密密钥可以交给企业自己的 KMS 按桶管理。点击「写入一批对象」，看检测如何工作。

私有预览

示意：对象名称与检测结果为演示用；功能处于私有预览阶段，以正式发布为准。

对象级勒索检测检查什么

恶意扩展名：已知勒索软件使用的文件扩展名。
扩展名与内容不符：比如 .jpg 里装的不是图片。
文件头异常：缺失或不匹配的头部信息。
熵值：部分或全部被加密的内容。
检测与 PUT 同时进行；可疑对象出现在桶的专门页签和审计日志里，可以自动拦截。

SSE-KMS：用自己的 KMS 管密钥 产品方向

在 Grid Manager 定义 KMS，租户在桶配置里选用；支持 Thales CipherTrust、HashiCorp Vault、Entrust。
密钥会被缓存，减少对 KMS 的调用。
开放湖仓 · 01

二十年来，「表」这一层去了哪里

数据仓库有表也有事务，但贵、难扩展；Hadoop 用 Hive 元数据库记住哪些文件是表；数据湖把 Parquet 放进桶里，弹性有了，表却丢了；湖仓用 Iceberg 把表找回来，代价是要多运行一个目录服务。点击各阶段对比。

把表层拿走，规模一大就会出问题

并发写：没有原子提交。
加一列：一个字段变成一个项目。
治理：只能管前缀，管不到表。
开放湖仓 · 02

Iceberg：同样的字节，有了行和列

Iceberg 是开放的表格式标准。它在对象存储上写一层元数据，把一堆 Parquet 对象组织成表；数据本身不移动、不转换，Parquet 还是 Parquet。

五个词

对象存储：保存字节。
Parquet：字节的列式排列方式。
Iceberg 表：对象存储上的「含义」。
目录（catalog）：表的索引。
查询引擎：执行 SQL，只是客户端。

找回的四种能力

原子性：读者不会看到写了一半的变更。
快照隔离：有人写入时，查询结果不漂移。
模式演进：加一列不用重写全部文件。
时间旅行：可以读任意历史版本。前两项接近 ONTAP 快照的概念。
开放湖仓 · 03

自己运行 Iceberg：表要维护，目录也要运维

表需要持续维护：合并小文件、过期旧快照、清理无引用文件。目录则是另一套生产系统：选型、数据库、高可用、安全，还要同步第二套身份体系。

1,536 → 6同样的行，文件数减少 99.6%
2 s → 0.1 s查询开始读数据前的规划时间

合并效果为 Dremio 工程博客中的示例，非 NetApp 基准测试。

表的三项日常维护

合并（compaction）：小文件进，大文件出。
快照过期：释放旧版本。
清理：删除没有被引用的文件。
不要对表所在的桶配置 ILM 过期规则，让快照过期机制决定删什么。

目录变成了你要运维的系统

① 选一个目录 ② 运行它的数据库 ③ 做高可用 ④ 做安全 ⑤ 同步第二套身份体系
常见的结果是：多站点 Iceberg 项目悄悄退化成单站点。
开放湖仓 · 04

StorageGRID Lakehouse Tables：把表层和目录放进存储里

NetApp Iceberg 目录内置在 grid 中，使用你已有的租户、密钥和策略；标准 Iceberg REST 接口与 S3 并列。目录不再是第二套生产系统。逐项对比自建与内置。

公开预览

公开预览功能，计划在 INSIGHT 2026 后至少 60 天的某个 StorageGRID 版本中提供，目前尚不可用，时间可能调整；表维护由 grid 执行属于后续规划。

六步启用

Grid 管理员：① 创建负载均衡端点 ② 为租户启用 Lakehouse Tables
租户：③ 创建桶并启用 ④ S3 组策略 ⑤ Iceberg 组策略
引擎：⑥ 同时指向 S3 端点和目录端点

多租户沿用现有租户

权限可以细到命名空间，甚至单张表。
例：finance 组只能看到 finance 命名空间下的 orders、invoices，看不到 marketing 的表。
开放湖仓 · 05

多站点数据湖：一个 grid、一个目录

自建时每个站点各有一个目录，彼此不知道对方：写入要写四份，站点之间没有协调，丢一个站点就要重建它的目录。目录内置在 grid 里之后，写一次、各站点一致，丢一个站点表还在。

示意：站点名称为举例。

为什么只有存储能做到

目录和数据存放在同一个多站点系统里，共享同一套复制、一致性和容灾机制。
grid 本来就是多站点的，目录跟着它一起多站点。

对制造业的意义

多工厂一个数据湖：各厂区就近写入质量与生产数据，总部直接查询全局视图。
厂区故障不影响分析：一个站点离线，其他站点的表与目录照常可用。
开放湖仓 · 06

每个任务选自己的引擎，数据只有一份

同一套表、同一批版本，用同一个接口访问。批处理用 Spark，交互式 SQL 用 Trino，流处理用 Flink，临时看一眼用 DuckDB；Databricks 通过开放共享连接器直接读取，不复制数据。

AI 训练最常被问的问题：「第 3 版用的是哪些数据？」

一个文件夹：没法要求「把桶恢复到三月份的样子」。
一个命名版本：训练前给表打上 train-v3 标签，十八个月后仍能读到同样的行。

NetApp 开放共享连接器 早期体验

把 ONTAP、StorageGRID 上的 Delta / Iceberg 表以只读、零复制的方式共享给 Databricks，由 Unity Catalog 统一治理。
数据留在本地，沿用现有的安全、保留和访问策略。
迁移与实践 · 01

从 HDFS 与 Hive，分阶段迁到对象存储上的 Iceberg

计算与存储分离：计算层用容器化的 Spark、Trino、Flink，容量层用 StorageGRID，热元数据和高 IOPS 分析放在 ONTAP AFF 上。迁移分四步，不需要停应用。点击步骤查看。

迁移与实践 · 02

两个实践：查询更快，硬件更少

NetApp 自己的 AutoSupport 分析平台每天接收 4–5 TB 遥测数据，从 Hive + HDFS 迁到 Dremio + StorageGRID；一家全球一级银行在 StorageGRID 上运行 1.5 PB 的 Iceberg 湖仓。

> 60%计算资源减少
10–20×查询提速
30%TCO 下降

全球一级银行 · 1.5 PB 湖仓

规模：1.5 PB 数据放在 StorageGRID 上，没有额外副本。
吞吐：Spark 批处理与 Trino 即席查询并发，持续读写最高约 50 GB/s。
迁移：用 XCP 与 DistCp 从 HDFS 分阶段迁移，应用不停机。
35–45%TCO 下降（免去 Hadoop 软件许可、缩减容量）
Object Lock不可变保留，满足监管审计

两个案例的数字均为客户在自身环境中的观测值，依据 BKO1002、BKO1026 场次资料。

总结

存储成为记录系统，每个引擎都来存储取数

事实只保留一份，就在你已经运行的地方，而不是另存一份副本。
