零 RPO
对象存储的零数据丢失、零业务中断

质检影像、产线数据归档、PLM 文件和备份库都在往对象存储上走，这些数据一旦丢失就很难补回。StorageGRID 把多个站点组织成一套网格、一个命名空间：元数据跨站点仲裁确认，对象按 ILM 规则同步放置，任意一个站点整体失效，读写不中断、数据不丢失，也不需要执行切换流程。

How it works · 01

零 RPO 的前提：元数据一致，对象可达

故障发生的那一刻，元数据和对象内容都已同步且一致，对象在故障后仍然取得到，才谈得上 RPO=0。StorageGRID 用一致性模型管元数据，用 ILM 管对象放置，用负载均衡管访问路径。

How it works · 02 · Consistency

桶一致性级别：在一致性与可用性之间选位置

一致性在桶级别设置，可随时调整。只有跨站点强一致的两个级别满足零 RPO。点击表格中的级别查看行为。

一致性级别跨站点强一致零 RPO
All所有节点立即收到满足
Quorum Strong-global跨站点仲裁确认首选
Legacy Strong-global是（两站点采用）部分
Strong-site否，仅站点内不满足
Read-after-new-write否，更新最终一致不满足
Available否，全部最终一致不满足

行为

运维提示

一致性是桶级别设置，可随时调整，不同业务的桶可以用不同级别。
站点故障期间若必须优先恢复写入，可把桶临时降到 read-after-new-write 或更低，故障恢复后再调回。
How it works · 03 · Quorum

元数据仲裁：丢掉一个站点，还够不够数

每个站点保存 3 份元数据副本。Quorum Strong-global 要求写入被仲裁数的副本确认才返回成功。调整站点数、点击站点模拟失效，看仲裁是否仍满足。

站点数3
点击站点切换在线 / 失效
可达的元数据副本 失效站点
9元数据副本总数
5仲裁数
9当前可达副本

结果

仲裁数怎么算

仲裁数 = 1 + (站点数 × 3) ÷ 2 # 取整 # 3 站点：1 + 9 ÷ 2 = 5，任意单站点失效后剩 6 份 ≥ 5
两站点采用 Legacy Strong-global，单站点故障时 GET / HEAD 不中断，部分写入类操作中断。
第三站点可以只放仅元数据节点，凑齐仲裁而不必配齐对象容量。
How it works · 04 · ILM ingest

ILM 摄取行为：返回成功之前，对象放到了哪里

同一个 PUT，三种摄取行为决定了返回 200 时对象是否已经按规则放到多个站点。切换行为与场景，对比正常和站点 2 不可达时的结果。

按规则放置的对象 临时副本（尚未按规则放置） 排队待放置

Balanced 平衡

选型建议

Strict 放置绝对精确，代价是故障期间写入直接失败，需要应用具备重试能力。
Balanced 在可用性与一致性之间取平衡，是多数部署的推荐配置；多站点零 RPO 参考架构采用 Balanced。
Dual commit 先落两份再异步放置，不满足零 RPO。
How it works · 05 · Failure domains

四层故障域，每一层都在本层内消化

磁盘、节点、站点、网格逐层嵌套。下层故障不外溢到上层：单盘故障在节点内重建，单节点故障不影响站点，单站点故障不影响网格。

磁盘级

本地重建
不占站点间带宽
节点内纠删码在本节点磁盘间重建，站点间链路只承担同步复制。
逐层兜底
下层扛不住才上升
站点内保护处理节点故障，跨站点放置只为整站点失效兜底。
Deployment · 01

站点数量决定保护级别：三站点起才是完整零 RPO

两站点可用，但站点整体失效时部分写入会中断；三站点及以上做到任意单站点失效读写不中断。第三站点可以只放元数据节点。

Deployment · 02 · Dual grid

四地双网格：网格内同步，网格间异步

两套 StorageGRID 各 3 个站点：2 个存储站点加 1 个仅元数据站点，仅元数据站点放到对方区域。网格内零 RPO，网格之间用跨网格复制（CGR）再叠一层区域级冗余。

架构要点

每套网格 3 站点：2 个存储站点 + 1 个仅元数据站点
网格 1 的元数据站点在区域 2，网格 2 的元数据站点在区域 1
网格内 Balanced ILM 同步跨两个存储站点做纠删码放置
网格之间 CGR 双向异步复制桶、对象、版本与元数据
合计每个对象 4 份纠删码副本、18 份元数据副本

对客户的意义

用仅元数据节点凑齐第三站点，避免在四个地点各存一份对象的容量浪费。
同城零 RPO，异地区域级容灾；任意单个地点失效，两套网格的业务都不中断。
Deployment · 03 · Erasure coding

跨站点纠删码：同样扛住一个站点，容量少一半

三副本意味着 3 倍裸容量。跨 3 个站点做纠删码，在同样的站点级容错下把开销降到 1.5 倍。选择保护方式、拖动数据量，估算裸容量。

有效数据量1.0 PB

示意估算：未计入元数据、预留空间与节点内纠删码开销；可用的纠删码方案以所用版本的官方文档为准。

1.5 PB所需裸容量（3 站点合计）
1.5×容量开销

三个层次的纠删码

节点内：设备在节点内所有磁盘间做纠删码，多盘故障本地重建，不占站点间带宽。
站点内：在站点内多个节点间做纠删码防节点故障，如 4+2 需至少 6 个节点。
跨站点：在 3 个及以上站点间做纠删码，以低于副本的开销获得站点级容错。
可与副本混用：不同桶、不同租户、不同对象走不同 ILM 规则。

适合的数据

大容量、长留存的质检影像、产线历史数据、备份副本与归档，是跨站点纠删码的主流对象。
Deployment · 04 · Load balancing

RTO=0 靠的是访问入口，不是存储本身

存储侧做了多站点复制、入口却只指向一个站点，站点故障时客户端照样连不上。切换入口方式，再注入站点 3 故障，看请求怎么走。

结果

设计要点

站点内：多个 Gateway 节点组成 HA 组，自动故障转移与回切。
站点之上：外部负载均衡器分发到各站点 HA 组，必须配置健康检查。
Gateway 默认只在本站点存储节点间均衡；可配置跨站点，但会把站点间时延加进客户端响应。
DNS 轮询或直连存储节点也能用，但不具备自动摘除能力。

Configuration · 02 · Performance

同步写入的性能，由最弱的那个站点决定

返回成功之前要等每个站点完成放置，所以吞吐最低、时延最高的站点决定整体写入表现。拖动各站点的处理能力与往返时延，看瓶颈落在哪里。

示意模型：整体写入吞吐取各站点处理能力的最小值，同步写入时延不低于到最远站点的往返时延；数值为相对值，不代表实际性能。

60整体写入吞吐（相对值）
≥ 8 ms同步写入附加时延

站点性能由什么决定

节点数量、CPU 核数与主频、内存
磁盘数量与类型
站点间链路带宽与时延

规划建议

三站点在节点数、CPU、内存、磁盘配置上尽量对等，避免一个站点拖累整体。
站点间存在明显时延或带宽瓶颈时，先评估写入时延影响，或改用跨网格异步复制。
